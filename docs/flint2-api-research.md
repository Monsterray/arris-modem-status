# Flint 2 local API evidence

Researched 2026-10-16. This research agent performed no router connections, credential reads, login attempts, package installation, or configuration changes. The parent task later retrieved anonymous public UI assets over its pinned TLS connection; those assets were inspected locally. Installed firmware version and authenticated response shapes remain unverified. Historical GL SDK4 packages and current upstream OpenWrt establish protocol families; the local public assets below establish this router's current browser login implementation.

## Current router public UI: verified implementation

The local GL GUI is served on HTTPS port 443 and LuCI on HTTPS port 8443, as reported by the parent task's anonymous checks. The GL index references `/js/app.bfe03abe.js`, whose dynamic view loader requests `/views/gl-sdk4-ui-<view>.common.js`. The `/login` route loads the `login` view. No whole application was executed for this inspection.

The current login view reads **only `alg`, `nonce`, and `salt`** from the challenge. It computes `crypt(password, "$" + alg + "$" + salt + "$")`, then `$getHash(username + ":" + cipher + ":" + nonce)`. The current app's `d714` module defines `$getHash` as **SHA-256 over UTF-8, lowercase hexadecimal output**. Therefore this observed UI uses outer SHA-256 even when the challenge omits `hash-method`; it does not read a challenge `count` or `rounds` field. The crypt module uses 1000 rounds for algorithm 1 and 5000 for algorithms 5/6 unless the crypt setting itself explicitly contains `rounds=`. Passlib must receive explicit 5000 rounds; its own SHA-crypt defaults are much larger.

The current RPC transport uses the real SID as the first `call` parameter; the UI's literal `"sid"` placeholder is replaced with the `Admin-Token` cookie value before sending. No additional network request signature appears in that transport. Current `home` calls confirm `system.get_info` and `system.get_status` with empty objects. Firmware display consumes `systemInfo.firmware_version` dynamically. Current `internet` consumes WebSocket `cable.status` rather than directly invoking historical `cable.get_status`; it also contains `cable.init_status`, whose side effects are unknown and should not be included in a passive collector.

The anonymous LuCI login page advertises `ubuspath: "/ubus/"`, form fields `luci_username`/`luci_password`, and `luci-base` asset version `git-22.335.71649-0ecaf74`. This is evidence for that firmware's endpoint path, not proof of authenticated access or ACL permissions. The upstream master `admin/ubus` default discussed later must not override this observed path.

### Independent synthetic authentication check

The inspected browser crypt module was evaluated in an isolated local VM supplied only native crypto and Buffer, with invented passwords. For username `root`, algorithm 5, salt `testsalt`, nonce `synthetic-nonce`, and password `fake-$@!-quote'"-space ` (including the final space), it produces cipher `$5$testsalt$nc9z20m.tnBESm5r5Ob0utfUa4y7md9LoetbHViSwX4` and outer SHA-256 `6504b12803a13aa68a4b9a929679932250327771d428520c4ff492c0e47b29f3`. Standard Unix-crypt/Passlib with explicit 5000 rounds agrees for this ASCII input, including literal shell-special characters.

**Non-ASCII limitation found:** the browser crypt code mixes JavaScript character lengths with UTF-8 hash updates. For invented password `café-$@!` with that salt/algorithm, browser cipher is `$5$testsalt$IlDwVBwAsEaK4/YS2YlSDyXkl0rP80IbssXeHVN2Nv4`, while standard UTF-8 SHA256-crypt gives `$5$testsalt$vPpA4.3CtPbLZRGOALGyRw0.aMd6OBM1Pz2jAJw1D9/`. Algorithms 1 and 6 also differ for this input. Preserve password bytes in encrypted storage, but do not claim browser-compatible non-ASCII GL authentication using a standard crypt library alone. Either implement a verified compatibility profile or reject unsupported input **before** credential submission; never test both derivations against the router.

## GL.iNet web GUI: confirmed historical protocol

The manufacturer's public SDK4 login package explicitly sends `challenge` with a username, reads `alg`, `salt`, and `nonce`, derives a Unix-crypt password with setting `$<alg>$<salt>$`, then computes the lowercase hexadecimal MD5 of `username:cipher:nonce`. It passes `username` and `hash` to `login`; the result contains the session ID used as `Admin-Token` by the UI. This is challenge-response authentication, not transport encryption.

Primary artifact: [official login IPK, pinned repository commit c783e6e](https://github.com/gl-inet/glinet/blob/c783e6ee1f2abfea2c70c11e0cc2d80c00d5c989/ipq807x/gl-sdk4-ui-login_git-2022.266.26020-6fbd5c2-1_arm_cortex-a7.ipk), SHA-256 `b13d8bbefbdaa7587c237385e25a343f5c2481243992f952772591c39a6f6eed`. Inspected `www/views/gl-sdk4-ui-login.common.js.gz` offline.

The matching core package confirms JSON-RPC 2.0 POSTs to `/rpc`, monotonically increasing IDs, response-ID checking, and authenticated calls with parameters `[sid, module, method, arguments]`. This implementation does not add a request signature. It also includes Unix-crypt algorithms 1 (MD5), 5 (SHA-256), and 6 (SHA-512), with default SHA-crypt rounds 5000. SHA-crypt is not a single SHA-256 digest or PBKDF2. The historical login UI does not supply a separate challenge `count` field.

Primary artifact: [official core IPK at the same commit](https://github.com/gl-inet/glinet/blob/c783e6ee1f2abfea2c70c11e0cc2d80c00d5c989/ipq807x/gl-sdk4-ui-core_git-2022.287.33493-a1930bc-1_arm_cortex-a7.ipk), SHA-256 `bc29847ad16c1c9b403487f485398dc6204f9cab53f77d9cc5e2b159aa101d40`. Inspected its app JavaScript offline. These 2022 artifacts target another chipset and predate Flint 2; they establish historical SDK4 behavior only.

**Cross-firmware limitation:** the official developer API site was unavailable during this research. The current public UI above resolves this router's outer hash behavior, but must not be generalized to every 4.x build. Do not treat `alg=5` as the outer hash or discover compatibility by retrying failed credentials. Accept only explicitly supported challenge fields/algorithms and make one login attempt. Nonce lifetime, firmware-specific optional challenge fields, and authenticated endpoint permissions remain unverified.

## LuCI and OpenWrt ubus are a separate protocol

Upstream `uhttpd` implements ubus JSON-RPC `call` with `[session, object, method, arguments]`. A `session.login` call uses the anonymous all-zero session and username/password arguments, returns ubus status plus session data, and is not GL's crypt challenge exchange. The password is transmitted to that endpoint, so authenticate TLS before sending it. A running LuCI UI does not prove that an external `/ubus` endpoint exists: it depends on server modules/configuration. [Pinned uhttpd implementation](https://github.com/openwrt/uhttpd/blob/7a06a9d5623af115d21a415866d85e7e903dcba5/ubus.c), [pinned rpcd session authentication](https://github.com/openwrt/rpcd/blob/d99f703e4035d03fbcfbada3cb697db346c2b984/session.c).

Modern upstream LuCI can instead POST `luci_username` and `luci_password` to its own login form, create an authenticated cookie, and proxy RPC under `admin/ubus`. That path uses LuCI authentication/CSRF/session handling; it should not be assumed interchangeable with a standalone `/ubus` or legacy `/cgi-bin/luci/rpc/auth`. [Pinned LuCI dispatcher](https://github.com/openwrt/luci/blob/b0cead459cfb434f2b2066e03f36c5bf39a583e7/modules/luci-base/ucode/dispatcher.uc), [pinned LuCI RPC transport](https://github.com/openwrt/luci/blob/b0cead459cfb434f2b2066e03f36c5bf39a583e7/modules/luci-base/htdocs/luci-static/resources/rpc.js).

Useful standard read operations are `system.board`, `system.info`, `network.interface.dump`, `network.device.status` for a named device, and `luci-rpc.getNetworkDevices` where installed/authorized. LuCI's network implementation consumes the latter's link carrier, speed in Mb/s, and duplex. Keep physical negotiated speed distinct from traffic counters and Wi-Fi PHY rates. ACL and package availability can reject individual calls; do not install/enable an API or alter ACLs automatically. [Pinned network reader](https://github.com/openwrt/luci/blob/b0cead459cfb434f2b2066e03f36c5bf39a583e7/modules/luci-base/htdocs/luci-static/resources/network.js), [read-access declarations](https://github.com/openwrt/luci/blob/b0cead459cfb434f2b2066e03f36c5bf39a583e7/modules/luci-base/root/usr/share/rpcd/acl.d/luci-base.json).

## Router-origin speed tests

GL.iNet documents **Network Quality from firmware 4.11**, including a router-local Cloudflare speed test reporting download/upload, latency, and bufferbloat. It is subject to SQM/QoS limits. The docs establish the feature, not a public RPC method or this router's installed version/support. Do not invent an API method or enable/change SQM simply to reach this feature. [Official Network Quality guide](https://docs.gl-inet.com/router/en/4/interface_guide/network_quality/).

A router-origin test removes the client Wi-Fi/LAN leg but can itself be limited by router CPU, VPN policy, shaping, test server, and single-connection behavior. Pair it with a wired-client test when assessing actual forwarding. A status read is passive; a speed test intentionally consumes WAN bandwidth and may affect other users. Use one finite, explicitly requested test at a time, preserve configuration, and identify whether the tested route traverses VPN/shaping. If the GUI API is unsupported, prefer an already-installed, known tool over downloading arbitrary binaries or executing shell through a general-purpose RPC endpoint. Optional key-authenticated SSH can run an existing tool separately; do not enable SSH or install packages automatically. No speed test was executed for this research.

## LuCI command execution for requested benchmarks

Upstream LuCI's `fs.exec(command, params, env)` invokes ubus object `file`, method `exec`; its wire arguments are a string `command`, optional string-array `params`, and optional string-to-string `env` table. `command` is an executable path or bare executable name; params are passed as argv entries via `execv`, with no shell parsing. The successful response object contains integer `code` (process exit status), and `stdout` / `stderr` strings when nonempty. LuCI documents the Promise rejecting on RPC failure. [Pinned LuCI `fs.js`](https://github.com/openwrt/luci/blob/b0cead459cfb434f2b2066e03f36c5bf39a583e7/modules/luci-base/htdocs/luci-static/resources/fs.js), [pinned rpcd `file.c`](https://github.com/openwrt/rpcd/blob/d99f703e4035d03fbcfbada3cb697db346c2b984/file.c).

Example ubus argument object shape: `{"command":"/usr/bin/curl","params":["--max-time","60","https://example.invalid/test"],"env":{}}`. Use a known executable path and explicit argv values; the sample URL is illustrative only.

rpcd defers the ubus reply while the child runs. The pinned rpcd source defines a 120,000 ms default timeout, and the daemon supports a startup `-t` override up to 600 seconds; on timeout it sends SIGKILL to the tracked command process and returns timeout status. The command does not get a detached job ID: its result arrives with process completion or timeout. Output buffers are capped separately at 256 KiB for stdout and stderr; filling a buffer fails with `not supported`. [Pinned rpcd timeout default](https://github.com/openwrt/rpcd/blob/d99f703e4035d03fbcfbada3cb697db346c2b984/include/rpcd/exec.h), [timeout configuration](https://github.com/openwrt/rpcd/blob/d99f703e4035d03fbcfbada3cb697db346c2b984/main.c), [execution and result handling](https://github.com/openwrt/rpcd/blob/d99f703e4035d03fbcfbada3cb697db346c2b984/file.c).

Thus a direct `curl` invocation with a 60-second curl max-time fits the upstream default 120-second rpcd execution window. This conclusion assumes a compatible rpcd build and no shorter HTTP/client timeout; the Flint 2's installed rpcd version, timeout override, `file.exec` ACL, and curl availability are unverified. LuCI's filesystem wrapper itself sets no shorter command timeout. If an HTTP client drops its request, do not assume this cancels the deferred rpcd child; rpcd's source only shows its own command timeout supervising that child. A speed-test invocation remains an intentional WAN-consuming action and should be fixed, bounded, and explicitly authorized. Avoid a shell wrapper: pass curl and each option as separate `params` entries, and keep output concise to fit the ubus cap.

## LuCI compatibility review

For browser-style calls, authenticate through LuCI's login flow and use the authenticated `admin/ubus` route/session handling. The observed Flint 2 login HTML advertises `/ubus/`, but that does not confirm its authenticated route or ACLs. A LuCI session cookie alone does not establish permission for `file.exec`: rpcd ACLs must grant the `file` object's `exec` method, and the file plugin is packaged separately as `rpcd-mod-file`. rpcd also performs executable/command-line ACL checks; any grant should narrowly constrain the executable and permitted arguments rather than use a wildcard. Actual firmware ACL/package state remains unverified. [Pinned LuCI dispatcher](https://github.com/openwrt/luci/blob/b0cead459cfb434f2b2066e03f36c5bf39a583e7/modules/luci-base/ucode/dispatcher.uc), [rpcd file execution](https://github.com/openwrt/rpcd/blob/d99f703e4035d03fbcfbada3cb697db346c2b984/file.c), [rpcd package definitions](https://github.com/openwrt/openwrt/blob/main/package/system/rpcd/Makefile).

Timeout behavior is narrower than a general process-tree cleanup guarantee: upstream rpcd defaults to 120 seconds, accepts startup `-t` values from 1 to 600 seconds, and on expiry sends `SIGKILL` to the tracked child PID before returning ubus timeout. A directly invoked `curl` is therefore bounded by this upstream path; rpcd source does not establish that arbitrary grandchildren are killed. Invoke curl directly with argv parameters, no shell wrapper. Output is capped at 256 KiB per stream. LuCI's `fs.exec()` wrapper defines no command timeout; a client-side HTTP timeout may still occur first, and a dropped request is not evidence that rpcd cancelled the child. [rpcd timeout constant](https://github.com/openwrt/rpcd/blob/d99f703e4035d03fbcfbada3cb697db346c2b984/include/rpcd/exec.h), [rpcd timeout option](https://github.com/openwrt/rpcd/blob/d99f703e4035d03fbcfbada3cb697db346c2b984/main.c), [timeout kill/reply](https://github.com/openwrt/rpcd/blob/d99f703e4035d03fbcfbada3cb697db346c2b984/file.c#L3676-L3687), [LuCI fs wrapper](https://github.com/openwrt/luci/blob/b0cead459cfb434f2b2066e03f36c5bf39a583e7/modules/luci-base/htdocs/luci-static/resources/fs.js).

Implementation implications: keep the speed-test and HTTP client deadlines below the router's rpcd cap, handle ubus timeout separately from curl exit status, and use a finite curl max-time. Router-specific endpoint, ACL, binary availability, and rpcd timeout override are unverified; no router or credentials were accessed for this review.

## Python dependency compatibility note

As of 2026-10-16, the project declares Python `>=3.9`. PyPI metadata says Requests 2.34.2 requires Python `>=3.10` (2.32.5 supports `>=3.9`), urllib3 2.8.0 requires `>=3.10` (2.7.0 also already requires `>=3.10`), and pytest 9.0.3 requires `>=3.10` (8.4.2 supports `>=3.9`). Therefore those newer releases cannot be unconditional upgrades while keeping the package installable on Python 3.9. [Requests 2.34.2](https://pypi.org/pypi/requests/2.34.2/json), [Requests 2.32.5](https://pypi.org/pypi/requests/2.32.5/json), [urllib3 2.8.0](https://pypi.org/pypi/urllib3/2.8.0/json), [urllib3 2.7.0](https://pypi.org/pypi/urllib3/2.7.0/json), [pytest 9.0.3](https://pypi.org/pypi/pytest/9.0.3/json), [pytest 8.4.2](https://pypi.org/pypi/pytest/8.4.2/json).

Keep the core Python 3.9 floor, and make the Flint 2/router-tool extra a Python 3.10+ support target: use Requests `>=2.34.2` and urllib3 `>=2.8.0` for that tool environment, while retaining Python-version markers/caps for core's 3.9-compatible dependencies. The urllib3 security fix has no Python-3.9-compatible release in this version line; either keep 3.9 away from the affected HTTPS-forwarding-proxy TLS configuration or raise the runtime floor if the fix must apply uniformly. Run Flint 2 tests and pytest 9.0.3 on Python 3.10+; the Python 3.9 CI job should exercise core only and omit the Flint 2 extra/router-tool tests. pytest 8.4.2 remains installable on 3.9 but is flagged by the supplied audit data, so don't represent it as receiving the 9.0.3 fix.

The implementation uses an internally generated `/bin/sh -c` command for the
finite `dd | curl` upload pipeline and diagnostic preflight. This is broader
execution than direct argv calls and requires the existing account's permission;
no ACL is changed to obtain it. Passwords never enter commands, dynamic device
names are validated and shell-quoted, and the CLI accepts no arbitrary command or
URL. Curl's own 60-second deadline bounds the transfer even if a local HTTP request
ends early; interruption is not advertised as cancelling the remote process tree.
