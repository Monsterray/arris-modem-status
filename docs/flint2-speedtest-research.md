# Flint 2 Cloudflare transfer baseline: research

## Endpoint shape

Cloudflare's own [`@cloudflare/speedtest` documentation](https://github.com/cloudflare/speedtest) identifies `https://speed.cloudflare.com/__down` as its download API and `https://speed.cloudflare.com/__up` as its upload API; its default measurements request downloads by byte count and POST uploads to the upload API. The script's `GET /__down?bytes=N` and binary `POST /__up` with `Content-Type: application/octet-stream` therefore match the official browser test's endpoint/method/body model. Cloudflare documents that results are collected on completion for aggregated connection-quality insights. The endpoints are a public testing interface, not a versioned service contract; avoid promising compatibility or treating the result as an official Comcast capacity certification.

## Upload buffering and a streaming option

The initial `dd ... | curl --data-binary @-` implementation sends the intended exact binary body and content type, but stdin-based `--data-binary @-` buffers stdin to determine its size before POSTing (curl project [discussion](https://github.com/curl/curl/discussions/18300)). `--upload-file -` reads stdin incrementally, but curl treats its length as unknown and normally uses chunked HTTP/1.1 transfer. There is a documented curl-users workaround for a known-length stream: override curl's generated transfer-encoding header with an empty `Transfer-Encoding:` header, provide the exact `Content-Length: N`, and force `--request POST` while using `--upload-file -`. Curl documents that a blank custom header removes an internally generated header, and its mailing-list archive shows this exact combination for streaming a known-size stdin body. The script now uses this form:

```sh
dd if=/dev/zero bs=1048576 count="$COUNT" 2>/dev/null |
  curl --request POST --upload-file - \
    --header 'Content-Type: application/octet-stream' \
    --header 'Transfer-Encoding:' \
    --header "Content-Length: $BYTES" \
    https://speed.cloudflare.com/__up
```

Here `BYTES` must equal `COUNT * 1048576`; a mismatch violates HTTP message framing and can hang or truncate the request. This retains Cloudflare's POST plus raw-body shape and avoids chunked transfer. `--upload-file` normally chooses PUT for HTTP(S), which is why `--request POST` is essential. The parent performed one controlled Mac-origin check on 2026-10-16 with exactly 1,048,576 generated bytes: Cloudflare returned HTTP 200 and curl reported exactly that upload size. This verifies endpoint acceptance with the Mac's curl; the router's installed curl remains untested, and this was not a router speed baseline.

## Measurement limits and accuracy

- A single sequential HTTP connection is useful as a router-origin path sample, but does not emulate Cloudflare's official browser test: the official engine ramps through many request sizes, repeats requests, and calculates a percentile, while this script uses one fixed-size curl transfer per sample and reports curl's whole-transfer rate. Short downloads can be dominated by connection/TLS setup and startup; larger transfers better expose sustained rate but consume more data and time.
- The script derives Mbps from curl `speed_download`/`speed_upload` and validates transferred byte counts. It should be described as application-layer HTTP throughput, not Ethernet/WAN line rate. TLS, TCP/IP overhead, retransmissions, request setup, remote edge load, and router CPU contribute. The report already records connection/TLS timings and CPU snapshots, which help interpret unusually low results.
- `--route wan` binds transfers to the detected WAN device but does not prove a VPN, policy route, or firewall rule was bypassed. Keep route and router load state beside each run; compare with a wired client for actual forwarding capacity.
- The original `--data-binary @-` could consume RAM proportional to the requested upload size. The final runner streams generated zeros with a declared size, avoiding that upload-sized buffer and any private-file input.
- For the lowest router overhead, begin with one run and modest byte counts, leave VPN/SQM/QoS in the intended operating state, and avoid concurrent traffic. A single HTTP flow also underuses high-capacity links when TCP window, congestion control, or router CPU is the limiting factor.
